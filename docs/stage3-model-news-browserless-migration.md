# Stage 3: moving Model News assertions out of Chromium

This is the coverage migration map for the first Stage 3 browser-test
optimisation PR. It records, assertion by assertion, what left the Chromium
Model News suite, where it went, what stayed in the browser and why.

Scope: **Model News only**. Memberships, Overview, Usage, Costs, Settings,
Reports and Sidebar are assessed at the end, not changed here.

## 1. What the suite looked like at the start

At `origin/main` (`8fff6e7`, generated by PRs #79 and #81):

| Metric | Before |
| --- | --- |
| `test/news-layout.test.mjs` cases (per-file budget) | 14 |
| Chromium launches for that file | 28 (12 grid + 16 probes) |
| Wall clock, single serial run | 94.5 s |
| Browserless cases (`scripts/node-tests.sh browserless`) | 794 across 27 files |
| Browserless wall clock | 108.7 s |
| `test/news-render.test.mjs` | 52 cases, 11.0 s |

The 12 grid launches are one per (fixture, scope, locale) group: the page fixes
the fixture, scope and locale before any React render, so the 24-case layout
matrix is spread across 12 page loads. The 16 probe launches came from the 11
cases that asked for an extra single-case run; the other three cases read the
grid's own results.

The probes are where the migration started: most of what they asserted was data,
copy and provenance — not browser behaviour.

## 2. Migration map

Classification: **Move** (the assertion relocates without weakening its
evidence), **Replace** (a lower-level test detects the same regression),
**Consolidate** (duplicate removed while distinct detection is preserved),
**Retain** (Chromium keeps it because it measures browser-specific behaviour).

All moves land in `test/news-render.test.mjs`, which already renders the real
`NewsPage` in jsdom against the real plugin bundle. The moved cases render the
**same payloads** as the browser matrix: the page-local fixtures were extracted
to `test/news-layout.scenarios.mjs`, which both renderers import, so a scenario
cannot drift between them.

region exists, a Details disclosure is present).

## 3. Regression parity and the negative controls

Every replacement was proved against a deliberately broken product before the
browser assertion was deleted. Each mutation was applied to `desktop/plugin.js`,
the replacement test was run alone, the file was restored (SHA-256 verified),
and the test was run again.

| Control | Regression injected | Detected |
| --- | --- | --- |
| M1 | the unsupported category falls back to a generic "No updates match" | yes |
| M2 | an empty archive reports a filter result instead of the source limitation | yes |
| M3 | the published limitation replaces a populated subscription filter | yes |
| M4 | a trimmed section silently claims to be complete | yes |
| M5 | an unjoinable headline loses its published source link | yes |
| M6 | a variant row attributes the family head's source to its own provider | yes |
| M7 | a merged event resolves to a single record, dropping one source | yes |
| M8 | the honest no-signals explanation becomes a generic no-results message | yes |
| M9 | the visible route from the empty For You to All Updates is dead | yes |

9/9 controls failed with the regression present and passed on the restored
source. No mutation was committed.

**Finding while proving parity:** the `plansource` fixture used by browser case
6 carried `sections: []`. A published briefing whose sections are all
unrecognised is discarded before its `unsupported` list is read
(`newsBriefingFor`), so the limitation could never fire and the case's two
assertions held whatever the `!planEventsInArchive` guard did. The fixture now
carries one renderable personal section, so the guard is exercised: removing it
fails M3. The browser case was therefore *weaker* than its name claimed; the
replacement is stronger.

## 4. What stayed in Chromium, and why

The suite keeps the 7 cases that measure something a DOM-only renderer cannot:

- **Computed layout and contrast** across 380/1200 px, dark/light, en/zh.
- **Overflow and scrolling topology** (no descendant vertical scroller).
- **Real visibility and reachability** after a navigation: a marked event, an
  open Details panel, a group revealed past the first page.
- **Focus lifecycle** — the destination focus after show-all/load-more, the
  keyboard tab order, the `focus-visible` ring, and the consumed-request
  behaviour after the reader edits the search box.

The grid's data assertions (row 9) are retained even though their content is
covered browserlessly. Two reasons, both deliberate:

1. They are the browser's **anti-vacuous evidence**. Overflow and contrast
   assertions over a page that rendered nothing pass silently; asserting that
   every fixture item mapped to a card and that each case rendered its expected
   initial page keeps the layout measurements honest.
2. They cost **no additional browser work**. They run over results the grid has
   already produced, so removing them would reduce no launch and weaken the
   guard above.

This is a Retain decision, not an omission: the classification is recorded here
so a later pass can revisit it with the measurement in hand.

## 5. Measurements after

| Metric | Before | After |
| --- | --- | --- |
| `news-layout.test.mjs` cases | 14 | 7 |
| Chromium launches, that file | 28 | 20 (−8, −28.6%) |
| Wall clock, single serial run | 94.5 s | 60.0 s (−36.5%) |
| Browserless cases | 794 | 802 (+8) |
| Browserless wall clock | 108.7 s | 97.1 s |
| `news-render.test.mjs` | 52 cases, 11.0 s | 60 cases, 12.4 s |
| Inventory consistency | green | green |

Measured on the Hermes VPS: Node v24.22.3, `/usr/bin/google-chrome`, one run at
a time with nothing else executing, each run cold (bundle built per process).
The launch count is not an estimate: `child_process.execFileSync` was wrapped by
a measurement-only `--import` stub that appended each invocation to a file, and
the totals (28 / 20) were counted from it. Wall clock is a single run per state;
the browserless totals moved by more than the added tests explain, so treat the
108.7 → 97.1 s delta as noise rather than a saving.

A later stage-2 change replaced the command-line lifecycle this table was
measured against: the suite now runs one Chromium process with an isolated
browser context per case. See
[stage-2-model-news-chromium-reuse.md](stage-2-model-news-chromium-reuse.md).
The case counts and assertion coverage in this document are unchanged by that
work; only the launch count and wall clock differ.

## 6. Risks and limitations

- **jsdom is not Chromium.** A copy or data assertion moved here proves the DOM
  the component produces, not that a browser paints it. Anything that only a
  real layout engine reveals — clipping, hidden text, paint order — stays in the
  retained cases, which still render the same fixtures.
- **`hasPathToAll` measured visibility.** The browser probe required the All
  Updates tab to have a client rectangle; jsdom can only assert that it exists
  and responds to a click. The `nosignals` case still renders in the grid, so
  its control row is measured for overflow, but "the tab is visible" is no
  longer asserted directly for that state.
- **One grid assertion is timing-sensitive.** During measurement the
  `realistic__foryou__380__dark__zh-CN` contrast-presence assertion failed once
  and passed on re-run. It is the known readiness race in this harness
  (`virtual-time-budget` firing before every root commits), not a change in this
  PR: the assertion and its fixture are untouched.

## 7. Next Stage 3 priorities (not implemented here)

Ranked by the ratio of assertions that do not need a browser to the cost of
proving parity. Measure each suite's launches first with the same wrapper used
above — the per-file call counts (`grep -c 'chromeDom(\|execFileSync'`) are a
starting bound, not the answer.

1. **Memberships (six browser files).** `memberships-cards`, `-clarity`,
   `-disclosure`, `-layout`, `-polish`, `-visibility` each run one case with
   layout *and* copy in the same body. Split reading-state copy, counts,
   request-payload validation and save-state transitions into
   `memberships-disclosure`/`memberships-clarity` browserless equivalents.
   Retain the 320 px allowance-grid regression, disclosure focus behaviour,
   below-fold navigation and real narrow-pane save interactions.
2. **Overview and Usage.** Financial semantics, ordering and persistence
   assertions can move to the existing component suites; retain responsive
   layout, overflow, scrolling, visual treatment and interaction. Both files
   build their page in one case, so parity work is per-assertion rather than
   per-case — expect assertion moves without a launch reduction until the case
   is split.
3. **Costs and Settings.** Same shape as Overview: move copy and ordering,
   retain computed layout and interaction. Costs has the largest
   money-semantics surface, so its negative controls are the most valuable.
4. **Reports and Sidebar.** Preserve the Stage 2 lifecycle (one Chromium
   process, per-target browser contexts). Move genuinely data-only assertions
   where justified, but keep keyboard accessibility, tooltip clipping, computed
   layout, SVG presentation and scrolling.
5. **Then re-measure the whole suite.** The Stage 2 rollout is unfinished; until
   it lands, per-file launch counts and process reuse both matter, and a launch
   saving in one file can be dwarfed by a suite that still starts a browser per
   test.
